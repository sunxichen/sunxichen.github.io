> 这是「任务型 Agent 的 Agentic RL 实践」系列的一篇。项目是一个公积金“边聊边办”的办事 Agent，基于 Qwen3，SFT 之后用 GRPO 风格的强化学习继续训练，训练框架是 OpenPipe ART，策略模型用 LoRA 训练，推理用 vLLM。

## 一条 rollout 长什么样

先交代一下背景，后面的很多判断都和这个结构有关。

办事 Agent 的一条 rollout，是一段**多轮对话**：Agent 说一句或调一个接口，用户模拟器回一句，Agent 再说一句……直到 Agent 选择结束对话。用户模拟器也是一个模型（一个单独微调过、训练期间冻结的模型），它按照任务里写好的用户画像来扮演用户，问到什么才说什么。

整个系统大致是这样的：

```text
                ┌──────────────────────┐
                │  策略模型 (vLLM)      │  ← 每步训练后要更新权重
                │  Agent：追问/调接口/结束 │
                └─────────┬────────────┘
                          │ 一轮一轮交替
      ┌───────────────────┼───────────────────┐
      ▼                   ▼                   ▼
┌───────────┐     ┌──────────────┐     ┌─────────────┐
│ 用户模拟器 │     │   沙箱        │     │  Reward     │
│ (vLLM,冻结)│     │ 业务接口+数据库 │     │ 终态比对/NLI │
└───────────┘     └──────────────┘     │ /LLM 复核    │
                                       └──────┬──────┘
                                              ▼
                                       ┌─────────────┐
                                       │ 训练器(LoRA) │
                                       └─────────────┘
```

一个训练步要采若干组、每组若干条这样的对话，全部采完、打完分，训练器再用它们更新一次 LoRA。更新完的权重要同步给策略模型的推理服务，下一步才能用新策略去采。

有两个特点决定了这个系统的性能特征：

1. **每条 rollout 是一条串行链。** 第 3 轮 Agent 要说什么，取决于第 2 轮用户回了什么，没法并行。一条 rollout 有十几轮，就要串行地等十几次生成。
2. **策略模型每一步都在变。** 这和普通的推理服务完全不同：普通服务的权重是固定的，而这里每训练一步，推理服务就要换一次权重。

## rollout 才是大头

刚开始跑正式训练时，最先发现的是几个配置问题。比如推理请求的并发上限设得太低，一步要 20 分钟左右，调高以后降到了两三分钟。再比如，训练器和用户模拟器在时间上是互斥的：rollout 时训练器闲着，训练时模拟器闲着，所以我把它们放在同一张卡上，省出一张卡。

但随着训练推进，模型学会了把事情问得更细，对话越来越长，平均轮数几乎翻了一倍，一步又涨到了 8 到 11 分钟。其中训练本身只有一两分钟，剩下的全花在 rollout 和打分上。

所以优化的重点很明确：让 rollout 变快。

### 一次“优化”，反而慢了一倍

接下来我做了一个看起来很合理的优化：既然每条对话都是一轮一轮地进行，那就把所有对话的“同一轮”攒在一起，打成一个批次发给推理服务。批处理嘛，一般都会更快。

结果每步时间从约 540 秒涨到了约 1130 秒，**慢了一倍多**。换了个配置再试，还是比原来慢一半以上。

回头想想，原因其实很清楚：

- vLLM 本身就会做 continuous batching，它会把同时到达的请求动态地拼在一起。客户端再攒一次批，没有任何额外收益。
- 攒批意味着要**等**：这一批里最慢的那个请求没回来，其他请求就都得等着。
- 原来各条对话的进度是错开的，有的在等 Agent，有的在等模拟器，有的在打分，各个组件的负载是交错的。攒批以后，所有对话被强制对齐到同一个节奏，所有对话一起等 Agent，再一起等模拟器，交错带来的流水线效果被打掉了。

这个改动后来被永久撤掉了。它给我的教训是：**在一个已经有动态调度的系统上，再叠一层静态调度，往往是负优化。**

## 忙碌，不等于利用率

为了搞清楚时间到底花在哪，我给 rollout 的每个阶段都加了计时：Agent 生成、模拟器生成、沙箱执行、打分。

结果看起来很“清楚”：Agent 生成占了累计忙碌时间的约 98%，模拟器、沙箱、打分加起来不到 4%。看到这个数字，第一反应是“Agent 推理太慢了，该优化推理”。

但我又看了一眼 Agent 那张卡的 GPU 利用率。在 rollout 阶段，**有 63% 的采样时刻利用率是 0**，平均利用率只有 18% 左右。

这两个数字放在一起看，就很说明问题了。Agent 的“忙碌时间”是把每个请求从发出到返回的时间加起来；可同一时刻在推理服务里跑的请求并不多，大部分时候 GPU 在空等。实际的有效并发，只有我设置的并发上限的一半左右。

GPU 为什么会空等？还是因为那两个特点：每条对话是串行链，而且各条对话结束的时间很分散。一步里，最快的一批对话不到一分钟就结束了，可最后几条要拖到十几分钟。拖尾的那段时间里，推理服务里只剩零星几个请求，GPU 大部分时间无事可做。

所以这个瓶颈不是“推理不够快”那么简单，它是**串行加长尾**造成的结构性问题。单纯堆推理能力，收益有限。

## 换小模型，结果没变快

当时策略模型是 8B。结构性问题一时解决不了，最直接的办法就是换一个更小的模型，让每一轮生成都更快。我在同样的数据上重新做了 SFT，评测下来 4B 和 8B 的效果基本持平，于是换成了 4B。

速度上，我原本预期能快一倍左右，实测在长尾部分只快了大约 1.5 倍。这已经有点让人失望了。可更奇怪的是，换成 4B 以后跑正式训练，**每步的时间和 8B 差不多**，依然是 8 到 9 分钟。

模型小了一半，一步的时间却没变。这说明有什么东西把 4B 的速度优势吃掉了。

## 插桩：一训练就慢

我给推理服务加了更细的日志，然后发现了一个非常明显的规律：**第 0 步很快，从第 1 步开始突然变慢。**

| 指标 | 第 0 步 | 第 1～4 步平均 |
|---|---|---|
| 生成吞吐峰值 | 约 1500 tok/s | 约 250 tok/s |
| 单次生成延迟（中位数） | 5.5 秒 | 42 秒 |
| 每个生成 token 的耗时 | 0.040 秒 | 0.291 秒 |

吞吐掉到了原来的**约 1/6**，延迟涨了 7 倍多。而且从第 1 步到第 4 步，这个慢是稳定的，不会越来越慢，也不会自己恢复。

第 0 步和第 1 步有什么区别？在我的训练设置里，RL 阶段是在 SFT 合并后的模型上**再训一个新的 LoRA**。第 0 步时，这个 LoRA 刚初始化。LoRA 的初始化方式是让增量（delta）为 0，即两个低秩矩阵里有一个全是 0，所以第 0 步的 LoRA 虽然被加载了，实际上不改变模型的任何输出。从第 1 步开始，LoRA 被训练过，增量不再是 0。

也就是说，同一套 LoRA serving 的配置、同一个 LoRA 秩，**增量为零时快，增量非零时慢 6 倍。**

在下这个结论之前，我先排除了几个其他的可能：

- **前缀缓存（prefix cache）被清掉了？** 不是。多轮对话里，前缀缓存的命中率非常重要，换 LoRA 版本有可能导致缓存失效。但日志显示命中率一直稳定在 94% 左右，没有变化。
- **请求在排队？** 不是。推理服务里等待中的请求数始终是 0，所有请求都被立即调度了，只是每个都跑得很慢。
- **加载 LoRA 本身很慢？** 不是。每次加载新版本的 LoRA 不到 12 秒，而且不会阻塞请求。

## 便宜的修法，都不够

定位到 LoRA 以后，我先试了一圈不需要改架构的修法，主要是 vLLM 里和 LoRA、CUDA Graph、调度相关的几个开关。每个变体跑两步，看第 1 步的吞吐：

| 变体 | 第 1 步吞吐变化 |
|---|---|
| 关闭 CUDA Graph，用 eager 模式 | +3%（但第 0 步慢了近一倍） |
| 关闭 chunked prefill | +6% |
| 关闭 CUDA Graph 对 LoRA 的特化（`cudagraph_specialize_lora`） | +11% |

最好的一个也只提升了 11%，离“恢复到原来的水平”差得很远。我当时定的门槛是至少快一倍，没有一个变体达到。

坦白说，**为什么非零的 LoRA 会慢这么多，我没有查到 kernel 层面。** 我没有做 GPU 层面的 profiling，只在一次运行里看到过 Triton 的 LoRA kernel 在做 JIT 编译的警告。还有一个我没能解释的地方：增量为零的 LoRA 也是走同一条 LoRA 计算路径的，它为什么就很快？正常情况下，LoRA serving 的额外开销是一些小矩阵乘法，远不到 6 倍的量级，所以这更像是踩到了某条慢路径，而不是 LoRA 本身的固有代价。

我能确定的是：慢在 LoRA serving 这条路径上，只在增量非零时出现，几个常见的开关都救不回来。在这种情况下，与其继续往底层钻，不如换一条**绕开这条路径**的方案。

## 第一次决策：不合并，去做异步

最直接的绕开方式，就是不让推理服务走 LoRA：每训练一步，把 LoRA 合并进基础权重，推理服务直接用合并后的完整权重。

但我当时没有选这条路。我当时的理解是，每步合并要写盘、重新加载推理服务，和训练框架原有的流程冲突很大，改动成本高。于是我把主线换成了**异步训练**：既然 rollout 慢，那就让 rollout 和训练同时进行，用训练的时间去掩盖一部分 rollout 的时间。

ART 里有一个现成的异步训练器（PipelineTrainer）。它的工作方式是：一批常驻的 rollout worker 不停地采样，每采完一组就放进队列；训练器从队列里取够一批就开始训练，训完更新权重，worker 接着用新权重去采。

异步带来的问题是**数据陈旧**：训练器在用第 $n$ 步的数据训练时，一部分数据其实是用第 $n-1$ 步、甚至更早的策略采出来的。我设置的陈旧度上限是 $k=1$：只允许比当前策略旧一步的数据进入训练，再旧的就丢掉。这是比较保守的做法，业界的经验是陈旧度越大，越需要额外的修正手段。

## 异步跑起来：更慢，还丢了一大片

实际跑下来，结果和预期完全相反。

**更慢了。** 异步训练每步时间的中位数，大约是同步训练的两倍。而且每步的时间在不断变长：第一步七十秒，到第十几步已经要二十多分钟。训练器经常一等就是十几分钟。

原因一部分还是 LoRA：异步训练用的也是 LoRA serving，非零增量的那个慢一点没少，日志里连续几个小时吞吐都只有每秒一百 token 左右。另一部分是我自己的配置问题：常驻的 worker 数乘上每组的轨迹数，超过了推理服务的并发上限，请求开始排队。

**丢了一大片。** 跑到第 14 步时，一共采完了 199 组，其中进入训练的只有 112 组：49 组因为太陈旧被丢掉，38 组因为组内方差为零被丢掉。总丢弃率接近 44%，光是陈旧丢弃就占了约四分之一。

**策略漂移也更明显。** 训练时重新计算的对数概率和采样时记录的相比，平均差异从 0.023 涨到了 0.048，重要性比率（新旧策略概率之比）的最大值到了 3.09，大约是同步训练的两倍。格式错误也比同步训练更早出现。

这里还有一个让我困惑了一阵的小细节：训练日志里“偏离策略的步数”经常显示为 2，可我明明设的上限是 1。查了代码才发现，日志的算法是“训练后的新步数减去采样时的步数”，比真实的陈旧度多了 1。所以实际上并没有越界，只是几乎每一步都顶在上限上。这种“日志口径和直觉口径差 1”的问题，不查代码很难发现。

我当时的结论是：**在 LoRA serving 很慢的前提下，k=1 的异步训练不成立。** 注意这个结论是有前提的，它只说明“在慢的 LoRA serving 下做异步不行”，并没有否定异步本身。

## 回到合并：框架其实早就支持

异步走不通，我只好回头重新看“每步合并”这条路。这次我认真读了 ART 的代码，才发现之前的判断是错的：**ART 本身就支持每步合并，而且不需要写盘，也不需要重启推理服务。**

它的做法是这样的：

1. **训练还是用 LoRA 训。** 训练器那边什么都不变，显存占用、优化器状态、checkpoint 都和原来一样。
2. **每步训练完，暂停推理服务的生成。**
3. **在训练器的显存里，原地把 LoRA 合并进基础权重。**
4. **通过 NCCL，把合并后的完整权重直接推送给推理服务**，推理服务在内存里替换掉旧权重。
5. **把推理服务对外的模型名改成新的版本号**，比如 `model@12`。
6. **在训练器那边把合并撤销**，恢复成“基础权重 + LoRA”，继续下一步训练。

这样推理服务看到的永远是一份普通的、完整的权重，不再走 LoRA 的计算路径。代价是每步要多一次权重同步，同步期间生成是暂停的。

合并以后，单次生成延迟的中位数回到了 3 到 6 秒，每个生成 token 的耗时回到 0.02 秒左右，和之前“增量为零”时是同一个量级，比非零 LoRA 时快了一个数量级。我需要说明一下：这组数据来自后来的一次正式训练，那次的硬件和对话轮数上限都和之前不同，不是严格的对照实验。但差距是数量级上的，方向很清楚。

### 合并这件事，本身也有坑

说到合并，还有一个更早踩过的坑值得一提。

RL 的起点是“基础模型 + SFT 训出来的 LoRA”合并后的模型。最初我是在 SFT 的训练环境里做的合并，然后把合并后的模型拿到 RL 的训练环境里用。结果在 RL 环境里，这个模型的表现明显变差：评测的严格成功率只有 0.625，违规率高达三成多，出现了大量格式错误。作为对照，不合并、直接用“基础模型 + LoRA”跑，严格成功率是 0.844，违规率为 0。理论上合并前后应该近似等价，现在却差了一大截。

查下来，两个环境里的 torch、transformers、peft 这几个库的版本不同，在一个环境里合并出来的权重，拿到另一个环境里加载后，和原始“基础模型 + LoRA”的输出对不上：同样的输入，logits 的最大偏差有 6.6 到 8.4。改成**在 RL 的目标环境里重新合并**以后，最大偏差降到 0.7 左右，取 argmax 的结果完全一致，严格成功率到了 0.906，违规率回到 0。

从那以后，我给“合并”定了一条规矩：在哪个环境用，就在哪个环境合并；合并完必须和合并前做一次输出比对，确认 logits 的偏差在合理范围内、argmax 一致，才能往下用。

## 合并以后，异步从机制上就走不通了

合并解决了吞吐问题。那么自然会想：现在 rollout 快了，是不是可以把异步再捡起来，叠加一次加速？

我又读了一遍异步训练器的代码，发现**合并和异步，在机制上是冲突的。**

关键在于“旧版本的策略还在不在”。

在 LoRA 模式下，推理服务可以同时挂多个 LoRA 版本（我当时设的是 2 个）。训练出新版本时，新的 LoRA 被加载进来；旧版本会一直保留，直到所有还在用它的 rollout 都结束了才卸载。异步训练器专门有一个“租约”机制来管理这件事：每个 worker 开始一组 rollout 时，先“租”下当前的版本，跑完再归还。所以一条正在进行中的对话，可以一直用它开始时的那个版本跑完，然后再由训练器判断“这条数据太旧了，丢掉”或者“还能用，拿来训练”。

合并模式下，情况完全不同。推理服务里**只有一份权重，只有一个模型名**。一次同步之后，旧的权重被覆盖，旧的模型名 `model@12` 也不存在了。这时候，一条还在进行中的对话，比如刚跑到第 5 轮，第 6 轮再去请求 `model@12`，就会得到“模型不存在”的错误。

这条对话跑了一半就断了，没有完整的轨迹，也就没有 Reward。它连“太旧了，丢掉”的那一步都走不到，只能作为异常处理掉。

你可能会想：把陈旧度上限设成 0，不就不会用到旧版本了吗？也不行。这个异步训练器没有全局的同步屏障：它只要从队列里凑够一批数据就开始训练，训完就更新权重，而这时其他 worker 可能正跑到某条对话的中间。陈旧度上限只决定“哪些采完的数据能用”，管不了“正在采的数据会不会被打断”。

需要说清楚的是，这个冲突是我**读代码分析出来的**，而不是真的跑出来的错误。我之前实际跑过的异步训练用的是 LoRA 模式，没有遇到这个问题。但机制上它是确定的，没有必要真的跑一遍去验证。

于是摆在面前的选项只剩这几个：

| 方案 | 结果 |
|---|---|
| 异步 + LoRA 多版本 | 语义正确，但回到了慢的 LoRA serving |
| 异步 + 合并 + 同步前等所有对话跑完 | 安全，但“等所有对话跑完”就等于同步，异步的重叠收益变成 0 |
| 异步 + 合并 + 按轮记录策略版本 | 允许一条对话的不同轮来自不同版本的策略，需要改训练器，也要重新论证训练的正确性 |
| **同步 + 合并** | 采完所有组、打完分，再训练、再同步权重。天然安全，最简单 |

我选了最后一个：**严格同步加合并权重**。这个选择背后的逻辑可以用一句话概括：**同步训练不需要旧策略和新策略共存，所以它能直接吃到合并带来的速度；异步训练需要旧策略共存，所以它吃不到。**

## “严格同步”到底有多严格

说到“严格同步”或者“严格 on-policy”，很容易产生一个误解：既然每一步都是用最新的策略采样、然后立刻训练，那训练时的新旧策略比值（重要性比率）应该恒等于 1，PPO 或 CISPO 里的截断（clip）就完全没有作用了。

在我的设置里，这个说法并不成立。

原因在训练器内部：一个训练步里采回来的所有轨迹，会被打包成很多条序列，训练器**逐条做一次优化器更新**。第一条序列更新时，策略确实和采样时完全一样，比率等于 1；可从第二条开始，策略已经被前面的更新改动过了，而用来对比的“旧策略概率”仍然是采样时记录的那份，比率就会偏离 1。一个训练步内部，通常有几十次这样的更新。

所以准确地说，“严格同步”严格的是**采样和训练的外层循环**：每一步的数据都来自上一步训练完的策略，不会有跨步的陈旧数据。在一个训练步的内部，仍然存在轻微的“离策略”。

这也是为什么损失函数的选择仍然有意义。我用的是 ART 默认的 CISPO 损失：它把重要性比率截断到一个区间里，但截断的是**作为权重的比率**，而且这个权重不参与求导。这样即使比率超出区间，这个 token 的梯度也不会像 PPO 那样被直接截成 0，只是权重被限制住了。在严格同步下，比率偏离 1 的幅度很小，CISPO 的截断区间（默认是 0 到 5）几乎不会被触发。所以在实践中，“严格同步 + CISPO”的行为和标准的 GRPO 非常接近。

我在训练里一直盯着几个指标：重要性比率的分布、被截断的 token 比例、新旧对数概率的平均差异。异步实验里，这几个指标都明显比同步时更大，这也是我判断“漂移变大了”的依据。

## 什么时候应该回到异步

最后想说的是，我并不认为“同步比异步好”。在大规模的 RL 训练里，异步是提升吞吐的主流方向，业界有大量工作在做这件事。我选择同步，是在“单机、多轮对话、合并权重、单一推理服务”这些具体约束下的取舍。

如果条件变了，我会重新考虑异步。我给自己定了几个前提：

1. **推理服务足够快，训练本身也已经稳定。** 先把同步训练跑稳，再引入异步这个变量。否则一旦效果不好，分不清是异步带来的问题，还是训练本身的问题。
2. **先跑陈旧度为 0 的异步。** 这是一个“控制组”：它用了异步的流水线，但不引入陈旧数据，效果应该和同步一样。如果这一步效果就不一样，说明流水线本身有问题。
3. **再对比陈旧度为 0 和为 1。** 只有当陈旧度为 1 时的策略漂移温和而且平稳、格式错误和违规没有上升、墙钟时间有实质收益，才把异步作为主线。

另一条路是让推理服务支持多个权重版本共存，或者支持“一条对话的不同轮来自不同版本”。业界的一些系统就是这么做的。比如 AReaL 的设计里，rollout 可以在权重更新时被中断，再用新权重继续生成，同时在损失函数里显式地处理新旧策略之间的差异；PipelineRL 则允许生成过程中直接更新权重，一条序列里的不同部分可以来自不同版本的策略。这些设计都需要训练框架和推理服务一起配合，不是改一个开关就能做到的。

相比之下，ART 的异步训练器是一个比较轻量的版本：它的异步发生在“组”的粒度上，一条轨迹不会跨越多个版本，也没有中断和继续生成的机制。这在 LoRA 多版本的模式下是成立的，但和合并权重天然不兼容。

## 回头看

这一路走下来，有几个地方我觉得值得记下来。

**第 0 步是一个很好的对照组。** 如果我当时只看第 1 步以后的数据，看到的只是“推理很慢”，很容易归因到模型太大、并发不够、对话太长。正是因为第 0 步的 LoRA 增量为零，它和第 1 步之间只差了“LoRA 是否被训练过”这一个变量，才让问题一下子聚焦到了 LoRA serving 上。很多时候，定位问题的关键不是找到更多数据，而是找到一个只差一个变量的对照。

**先读代码，再做决定。** 第一次决定“不合并”，是基于“合并要写盘、要重启”的印象，而这个印象是错的。如果当时花半天读一下框架的代码，可以省掉异步那一大圈弯路。后来判断“合并和异步冲突”，也是靠读代码，而不是先跑出错误再回头找原因。

**结论要带上前提。** “异步更慢”这个结论，前提是 LoRA serving 很慢；“必须同步”这个结论，前提是只有一份合并后的权重。这些前提一旦变了，结论就要重新评估。我现在回头看当时的记录，最有用的往往不是结论本身，而是结论旁边写着的那句“在什么条件下成立”。
