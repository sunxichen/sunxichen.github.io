> 这是「任务型 Agent 的 Agentic RL 实践」系列的一篇。项目是一个公积金“边聊边办”的办事 Agent，覆盖查余额、租房提取、购房提取、还贷四类业务；结束对话的方式有三种：办结、拒办、转人工。训练方式是 SFT 之后接 GRPO 风格的强化学习。

## 先说几个概念

GRPO 的基本单位是“组”：同一道题，让模型做 K 遍（比如 K=8），这 K 条轨迹就是一组。每条轨迹的“优势”是它的分数和组内平均分的差，再除以组内标准差：

$$
A_i = \frac{R_i - \operatorname{mean}(R_1, \dots, R_K)}{\operatorname{std}(R_1, \dots, R_K)}
$$

由此可以直接推出一个结论：**如果一组里 K 条轨迹的分数完全一样，标准差是 0，这组就没有任何训练信号。** 全对是这样，全错也是这样。模型做 8 遍全对，说明这道题它已经会了，没什么可学的；8 遍全错，说明它连一次正确的样子都没碰到过，也不知道该往哪里学。

所以训练框架里通常有一步“动态过滤”：每一步采完所有组以后，把组内方差为 0 的组直接丢掉，只用剩下的组算梯度。丢掉的组占多少比例，我叫它**丢弃率**。

丢弃率是我在 RL 训练里最先盯的几个指标之一。它直接告诉你，花了大把算力采回来的轨迹，到底有多少真正用上了。我在启动正式训练之前就定了一条规则：**累计丢弃率超过 50%，就停下来查采样。**

## 现象：丢了 94%，指标纹丝不动

第一次正式跑 GRPO，跑到三十多步时，丢弃率的均值大约是 **94%**。

换句话说，每采 100 组，只有 6 组能产生梯度。评测集上的严格成功率在 0.81 到 0.84 之间来回晃，看不出任何上升趋势。

其他指标倒都很健康：没有出现违规，KL 散度几乎为 0，梯度范数正常。训练没有崩，它只是**饿着**。

按事先定好的规则，我停了训练。这里有个小插曲：那台机器上的启动脚本写了“训练进程退出后自动关机”，为了省云服务器的钱。直接停训练，机器就跟着关了，我还没来得及把现场日志拉下来分析。所以我先把外层的启动脚本杀掉，再处理训练进程，这才把机器保住。后来我把这一条写进了操作手册：停训练之前，先确认停下来以后机器还在。

## 第一个判断，是错的

看到丢弃率这么高，我的第一反应是：**模型已经学饱和了。**

这个推理听起来很顺：丢掉的组大多是“全对”的组，说明模型在这些题上已经稳定做对了；SFT 做得够好，留给 RL 的空间就不大了。照这个思路往下走，下一步就该是加难题、或者换个更难的任务分布。

可是有一件事说不通：评测集上它明明还有不少题做不对，尤其是还贷类，SFT 之后的单次成功率只有 16% 左右。一个在还贷上只有 16% 成功率的模型，怎么会在训练里“全对”？

这让我意识到，“丢弃率高”其实可以有两种完全不同的原因：

1. **采到的题，确实没有方差。** 模型在这些题上已经稳定全对或稳定全错。这是 Reward 或任务难度的问题。
2. **根本没采到有方差的题。** 有信号的题明明存在，但采样器没把它们送进来。这是采样的问题。

这两种情况的丢弃率看起来一模一样，可修法完全相反。前者要改 Reward 或换任务；后者只要改采样器。在判断“模型饱和”之前，我应该先回答一个更基本的问题：**这几十步里，到底采了哪些题？**

## 三路证据

### 证据一：实际采到了什么

我把这几十步里保存下来的一千一百多条轨迹全部拉出来，按业务类型和结束方式分了一下桶。

结果是：**100% 都是还贷类任务**，其中九成以上的轨迹以“转人工”结束。查余额、租房提取、购房提取，一条都没有。而且，有 91% 的轨迹分数恰好等于这类任务能拿到的最高分。

也就是说，这几十步里，模型一直在反复做同一类题，而且几乎每次都做对。

### 证据二：为什么只采到这一类

接下来要回答：任务池里明明有四类业务，为什么只采到了还贷？

我用同样的随机种子、同样的参数，在本地把训练任务池重建了一遍，然后把它按顺序打印出来。

**排在最前面的 320 道题，全是“还贷 + 转人工”。** 第一道不是还贷的题出现在第 334 位。按训练消耗任务的速度，要到第 41 步左右才轮得到它，而那次训练停在第 36 步左右。

训练从头到尾，都没有走出这个“前置块”。

### 证据三：这一类题，恰好是模型最会的

最后一个问题：这一类题，模型到底会不会？

我按“业务类型 × 期望结束方式”分桶，看评测集上每个桶的成功率：

| 桶 | 占任务池比例 | 评测成功率 | 还能学的空间 |
|---|---|---|---|
| 租房提取 / 办结 | 41.4% | 0.975 | 几乎没有 |
| 还贷 / 办结 | 18.0% | **0.250** | 最大 |
| 查余额 / 办结 | 9.9% | 1.000 | 没有 |
| **还贷 / 转人工** | **9.6%** | **1.000** | **没有** |
| 购房提取 / 办结 | 9.1% | 0.735 | 中等 |
| 租房提取 / 转人工 | 6.9% | 约 1.0 | 没有 |
| 购房提取 / 转人工 | 4.1% | 1.000 | 没有 |
| 各类拒办 | 约 1% | 1.000 | 没有 |

三条证据放在一起，结论就很清楚了：在“还贷”这个大类里，模型真正不会的是“还贷 / 办结”（成功率 25%），而训练偏偏一直在采“还贷 / 转人工”，这恰好是还贷类里唯一一个已经全对的子类。

不是模型饱和了，是采样器一直在喂它已经会的题。

## 根因：一个保底配额，兼职当了排序键

为什么“还贷 / 转人工”会被排在最前面？这要从一个“保底配额”说起。

SFT 之后的评测里，还贷是表现最差的一类业务：单次成功率低，违规也多。我当时担心，还贷任务在整个任务池里占比不算高，RL 阶段可能被其他业务稀释，学不到。尤其是“还贷 / 转人工”这类边界情况，我希望它在训练里有足够的出现次数。于是在构建训练任务池时，我加了一个保底配额：任务池里至少 20% 是“还贷 + 转人工”的任务。

问题出在实现上。构建任务池的逻辑大致是这样的（简化后）：

```python
priority = [u for u in units if is_loan_escalate(u)]
rest = [u for u in units if not is_loan_escalate(u)]
rng.shuffle(priority)
rng.shuffle(rest)

n_floor = ceil(max_tasks * 0.20)
selected = priority[:n_floor] + rest[: max_tasks - n_floor]  # 保底的放前面
pool = [task for unit in selected for task in unit]          # 展平
```

训练时，每一步按顺序从池子里取任务：

```python
def select_step_scenarios(pool, step, groups_per_step):
    start = (step * groups_per_step) % len(pool)
    return [pool[(start + i) % len(pool)] for i in range(groups_per_step)]
```

单独看，两段代码都没什么问题：池子里确实有两次洗牌，取任务时也确实会把整个池子轮一遍。可两段放在一起就出事了：洗牌只在“保底组”内部和“其他组”内部分别进行，**两组之间没有混合**，保底的那 20% 被整块放在了最前面；取任务又是顺序取，于是前四十步左右只能取到这一块。

“保底配额”本来只应该决定“这类题在池子里有多少”，结果它同时决定了“这类题排在哪里”。它兼职当了一个排序键。

还有一个更深层的原因：这个保底配额是在我拿到“各个桶到底学得怎么样”的数据**之前**定的。当时只知道“还贷整体很差”，就假设“还贷 / 转人工”也需要保护。等分桶数据出来，才发现还贷的问题全在“办结”，“转人工”早就学会了。保底配额保护的，恰恰是一个最不需要保护的桶：它在自然分布里只占 9.6%，被我硬拉到了 20%，还挤掉了真正需要训练的“还贷 / 办结”。

另外还有一个巧合。配额只在“从大池子里抽一部分题”时才会生效，而我当时的理解是正式训练会用整个任务池、不做抽样，所以以为它主要影响的是评测集的抽样。但正式训练实际上设了任务数上限，从几千道题里抽了一部分，配额就这样在训练池上生效了。一个我以为“不会起作用”的参数，悄悄起了作用。

## 修复第一步：配额只管“在不在”，不管“在哪”

修法本身很简单，两处改动：

1. **展平之前，把所有选中的单元整体洗一遍牌。** 不管有没有保底，保底的单元都会被打散到整个池子里。这样保底只决定“在不在、有多少”，不再决定“排在哪里”。
2. **保底配额默认值从 20% 改成 0。** 参数保留，可以配置，但我在文档里写明了：如果真要给某个桶设下限，最多设到和它的自然占比差不多，不要超过。

这里的“单元”需要解释一下。我的训练数据里有一种“对比对”：两道题只差一个关键事实，比如一个满足提取条件、一个不满足，答案分别是办结和拒办。这样的两道题被看作一个单元，洗牌时整对一起移动，不会被拆开。（不过它们在训练里是**各自成组**的：GRPO 比较的是同一道题的多次尝试，而不是一对题的两侧。）

修完以后，我没有接着之前的训练继续跑，而是从头开始。之前那十来次有效的梯度更新全部来自“还贷 / 转人工”，接着跑的话，修复前后的效果就混在一起，说不清楚了。

结果：**累计丢弃率从约 94% 降到了 43%。**

各个桶也都开始进入训练了。按桶看丢弃率：

| 桶 | 丢弃率 |
|---|---|
| 还贷 / 办结 | 3% |
| 购房提取 / 办结 | 16% |
| 租房提取 / 办结 | 48% |
| 查余额 / 办结 | 57% |
| 各类转人工、拒办 | 90%～100% |

“还贷 / 办结”和“购房提取 / 办结”几乎每组都能产生信号，正是之前分析里“还能学”的两个桶。

## 活着的组，也未必在学正事

43% 低于 50% 的警戒线，按规则可以继续跑了。但我又多看了一眼，发现了两个问题。

第一个问题：**丢弃率在上升。** 前 10 步是 34%，后 10 步是 52.5%，最后 5 步到了 62.5%。随着模型变强，越来越多的题变成“全对”，自然采样的浪费只会越来越多。

第二个问题更隐蔽。被丢掉的组里，有一半以上来自“租房提取 / 办结”。这个桶在评测上的成功率已经接近 99%。可是它仍然有大约一半的组被**保留**了下来，这让我很好奇：一个几乎全对的桶，组内的方差是从哪里来的？

我把这些组的分数拉出来一看，同一组里的分数大概是 0.71、0.73、0.75 这样。差别只有百分之二到四，而且全部来自**轮数扣分**：同样办对了，有的多绕了一轮，有的少绕了一轮。

也就是说，这些“活着的组”确实产生了梯度，但梯度教的不是“怎么把事办对”，而是“办对的前提下少说一句话”。这不是完全没用，但它和我最想让模型学的东西关系不大，而且它在每一步的梯度里占了不小的份额。

这让我意识到：**丢弃率只告诉你有多少组“有方差”，不告诉你方差来自哪里。** 一组的方差如果完全来自次要项，它对主要目标的贡献可能很小。

## 修复第二步：按组内方差分配采样名额

自然采样的问题在于，它按“任务池里有多少”来分配名额，而不是按“哪里能学到东西”。“租房提取 / 办结”在池子里占 41%，就拿走 41% 的名额，哪怕它几乎学不到什么了。

所以第二步，我把每一步的采样名额分成了三部分。

**大约 3/8 的名额定向分配给“组内最可能有方差”的桶。** 权重怎么定？我没有拍脑袋，而是直接用上一轮实测的数据：每个桶里，有多少比例的组真的有方差（也就是没被丢掉），再乘上这个桶在评测上还有多少提升空间。按这个算法，“还贷 / 办结”和“购房提取 / 办结”的权重分别是 0.74 和 0.26。

**大约 5/8 的名额仍然按自然分布来采，但排除了已经确认“学不到东西”的桶。** 判断标准是：实测丢弃率 90% 以上，而且评测成功率 95% 以上。这两个条件同时满足，才说明这个桶确实已经学会了，而不只是难。

为什么还要保留这么多自然采样？因为完全切到“高信号”的桶会有两个风险。一是**分布漂移**：模型只做还贷和购房，其他业务可能慢慢退化。二是**边界塌缩**：高信号的两个桶期望的结束方式都是“办结”，只训它们，模型可能越来越倾向于办结，在该拒办、该转人工的时候也选办结。自然采样那部分起到“压舱石”的作用。“租房提取 / 办结”虽然学不到多少东西，我也把它留在了这部分里，只是不再给它定向名额。

**每 4 步插入一组“转人工”的题，作为哨兵。** 转人工的桶已经被排除在自然采样之外了，但我还是想知道模型在这个边界上有没有退化。哨兵组的主要作用是**监控**，而不是贡献梯度：它被丢掉没关系，只要它某一天开始出现“做错”的情况，我就能马上看到。

有一条规则我特意写进了设计文档：**不要“越难越采”。** 直觉上，难题应该多练，但对 GRPO 来说，一道成功率接近 0 的题和一道成功率接近 1 的题一样，组内都没有方差，都学不到东西。真正有信号的是那些“有时对、有时错”的题。“难”和“能学”是两回事。

还有一个设计上的取舍：这一版的权重是我看完诊断数据后**手动定的**，固定在配置里，而不是让程序在训练过程中自动调整。自动调权听起来更“智能”，但它会让训练过程中的采样分布一直在变，出了问题很难复现和归因。我选择先用一个简单、可解释的版本验证思路，自动调权留作后续。

上线以后，前几步的丢弃率降到了 13% 左右。不过要说清楚两点：一是我只观察了最初几步，模型变强以后丢弃率大概率还会回升；二是同一轮里我还改了 Reward 的满分上限，两个改动混在一起，没法严格分开各自的贡献。当时算力有限，我选择了接受这个归因上的不干净。

## 一个被否决的提议：把满分调到 1.0

排查过程中有一个提议，我觉得值得单独说一下，因为它涉及 GRPO 一个很基础的性质。

当时的 Reward 设计下，一条完美的轨迹最高只能拿到 0.75 或 0.8，因为一部分权重分给了扣分项。看到 91% 的轨迹都卡在 0.8，我自己也冒出过一个想法：是不是把满分调到 1.0 会好一点？毕竟“满分是 1”看起来更符合常理。

这个提议对丢弃率**没有任何作用**。原因就在优势的计算方式上：

$$
A_i = \frac{R_i - \operatorname{mean}(R)}{\operatorname{std}(R)}
$$

如果把所有分数乘以一个正数 $a$、再加一个常数 $b$，也就是 $R_i' = aR_i + b$，那么平均分变成 $a \cdot \operatorname{mean}(R) + b$，标准差变成 $a \cdot \operatorname{std}(R)$，代入以后：

$$
A_i' = \frac{aR_i + b - a \cdot \operatorname{mean}(R) - b}{a \cdot \operatorname{std}(R)} = A_i
$$

优势完全不变。一个全是 0.8 的组，缩放后变成全是 1.0，标准差仍然是 0，仍然会被丢掉。

（严格来说，如果实现里不除以标准差，乘以 $a$ 会等效地放大学习步长。但不管哪种实现，“全同分的组仍然全同分”这一点都不会变。）

调满分不能解决问题，还会带来成本：和之前的训练、和 SFT 基线的分数都不可比了。所以作为丢弃率的修法，我否决了它。

后来 Reward 确实也调整过满分上限，但那是出于另一个原因：调整各项之间的相对比例，让“办对了的轨迹之间”能有更好的区分度。那次调整不是线性缩放，而且和丢弃率无关。

真正能改善“成功轨迹之间没有区分度”的，是**拉开顶部**：让“办对且高效”比“办对但绕了路”分数更高。这是改变分数的相对结构，而不是整体平移或缩放。

## 后来：从“按桶分配”到“按题筛选”

上面的方案是按“桶”来分配名额的。它有一个固有的局限：一个桶内部，题和题之间的差别可能很大。“还贷 / 办结”整体成功率 25%，但里面有的题模型一次都做不对，有的题已经稳定做对了。按桶分配，还是会采到很多没有信号的题。

所以后来，我把筛选的粒度从“桶”细化到了“题”。

做法是：在正式 RL 之前，用 SFT 模型把每道候选题都做 8 遍，记下做对了几遍。然后：

- **做对 0 到 1 遍**：太难，或者题本身有问题，不进入训练，单独诊断；
- **做对 2 到 6 遍**：这是“有时对、有时错”的区间，进入训练；
- **做对 7 到 8 遍**：已经基本学会了，只用来监控是否退化。

为什么 1 遍不算、要 2 遍以上？因为只做对 1 遍，很可能只是碰巧。阈值收紧到 2 到 6，可以减少因为一次偶然的成败而误判的情况。

这个思路背后有一个简单的计算。假设模型做一道题的成功率是 $p$，一组做 $K$ 遍，这组“有方差”的概率是：

$$
P(\text{有方差}) = 1 - p^K - (1-p)^K
$$

减去的两项，分别是“全对”和“全错”的概率。以 $K=8$ 为例：

| 单次成功率 $p$ | 0.02 | 0.16 | 0.5 | 0.9 | 0.98 |
|---|---|---|---|---|---|
| 组内有方差的概率 | 0.149 | 0.752 | 0.992 | 0.570 | 0.149 |

有两点值得注意。第一，这个函数关于 $p = 0.5$ 对称：成功率 2% 的题和成功率 98% 的题，有信号的概率一样低。这正是“不要越难越采”的数学依据。第二，单次成功率只有 16% 的题，在 8 次采样下有 75% 的概率产生信号。这也是我判断“还贷 SFT 后只有 16%，不需要回去补 SFT 数据，可以直接进 RL”的依据之一。看一道题能不能被 RL 学，看的是 pass@k，而不是 pass@1。

按题筛选和按桶分配，背后是同一个原理，只是粒度不同。而且按题筛选是在训练开始**前**做的，相当于“先挑好米再下锅”，比在训练过程中调整采样分布更根本。

这个方法也有一个它自己解决不了的问题，我觉得值得记一笔：**GRPO 看不见“训练集上永远做对”的弱点。** 如果某类题在训练任务上模型总是全对，这类题就永远进不了梯度。可如果模型在训练任务之外的同类题上表现不好，比如换一种说法、换一组数据就出错，RL 是修不了的，因为它根本采不到失败的样本。这不是采样器能解决的问题，它需要在任务构造上增加多样性，让训练任务本身就覆盖到模型的弱点。

## 和业界做法的对照

做这些的时候，我是从自己的问题出发的，没有参考特定的工作。事后回头看，有几个思路是相通的。

**DAPO 的 Dynamic Sampling。** DAPO 的做法是：采样时一旦发现某组全对或全错，就丢掉并继续补采，直到凑满一个批次的“有方差”的组。这保证了每一步的有效批次大小是稳定的。代价是额外的采样开销：丢弃率越高，需要补采的越多。我看到的估计是需要多付出 1.5 到 2 倍的采样成本。

我的做法偏向另一个方向：**在采样之前**把名额分配好，尽量少采没信号的题，而不是采完了再丢。两者并不冲突。后来我在一个版本里也加了有上限的补采：某组被丢了，就从同一个桶里换一道题补上，但每步最多补一定的数量。

**按通过率过滤题目。** 只保留通过率严格介于 0 和 1 之间的题，这在推理类 RL 里已经是很常见的做法。我后来“按题筛选”的方法，本质上就是这个。

## 最后说一个日志上的教训

排查过程中，还有一个小问题差点误导我。

训练框架会把每一步的轨迹保存下来，方便事后分析。但它的保存逻辑是：**如果这一步有梯度，就只保存被保留下来的组；如果整步都被丢了，才保存全部的组。** 于是用保存下来的轨迹去重算丢弃率，结果会系统性地偏低，因为被丢掉的组大多没被存下来。

好在业务类型和分数分布这两项不受影响，所以前面“证据一”的结论是成立的。但真正可信的丢弃率，只能看训练过程中实时记录的指标。

吃了这次亏以后，我在训练里加了一组按桶统计的过滤指标，直接从采样出来的原始组计算，而不是从保存下来的轨迹倒推：每个桶采了多少组、丢了多少组、丢掉的原因是全对还是全错。后来几次判断采样有没有问题，都是靠这组指标。

回头看整个过程，最关键的一步其实是第一步：在下“模型饱和了”的结论之前，先去看“到底采了什么”。这个问题问得越早，绕的弯路就越少。
